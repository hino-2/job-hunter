### 4.8 Sources and providers

`VacancySource` (values `'HH'` | `'GETMATCH'` | `'IT_VACANCIES'` | `'GEEKJOB'` | `'COMPANY_SITE'`,
§4.14) generalizes all sites behind one contract. The column is a plain `varchar(16)` with no `CHECK`,
so adding a value needs no migration (§3.1, §3.5).

- The enum lives in `applications/applications.constants.ts` next to `SyncOutcome`: module dependency
  runs `vacancies`/`hh`/`getmatch`/`company-sites` → `applications`, so a back-reference would be a cycle.
- **`VacancySourceProvider`** (in `vacancies/`): `source`, `parseUrl(url): string | null` (pure, never
  throws), `fetchVacancy(externalId): Promise<VacancyFetchResult>` (never lets an exception escape — any
  failure becomes a §4.5 outcome). Implemented by
  `HhApiService`/`GetmatchApiService`/`ItVacanciesApiService`/`GeekjobApiService` (§4.13) themselves.
  **`COMPANY_SITE` has no implementer** — `VacancyProviderRegistry`'s `byId` map never contains it,
  so `find('COMPANY_SITE')` returns `null` (sync yields `SKIPPED_UNSUPPORTED`, same as any other
  unrecognized source) and `resolveByUrl` simply never resolves any URL to it — a company career
  site's own host is never mistaken for one of the four sync sources.
- **`VacancyLeadSearchProvider`** (in `vacancies/`) is the second, independent contract — the lead
  search of §4.11: `source`, `readonly publicationDateKnown: boolean` (§4.11.4/§4.14 — `true` for
  hh.ru/it-vacancies.ru/geekjob.ru, `false` for `COMPANY_SITE`), `acquireRequestSlot()`,
  `fetchSearchPage({ searchUrlTemplate, page })`, `fetchVacancyDescription(item: VacancySearchItem)`
  (takes the whole search item, not just its `externalId` — `CompanySiteSearchService` needs
  `item.vacancyUrl` to pick a parser; the other three implementers destructure `externalId` as their
  first line and are otherwise unchanged), results discriminated by `ok`, not by `SyncOutcome` (a search
  page has no notion of "the vacancy is archived"). Implemented by `HhSearchService`,
  `ItVacanciesSearchService`, `GeekjobSearchService` (§4.13) and (§4.14) `CompanySiteSearchService`;
  **getmatch.ru implements only the sync contract** — it publishes no paginated results page we may
  crawl. Dispatch is `VacancyLeadSearchRegistry` in `vacancy-search/`, the mirror of
  `VacancyProviderRegistry` for the search lane.
- **`VacancyProviderRegistry` is the single dispatch point**: `resolveByUrl(url)` returns the first
  recognized source + external ID (host sets do not overlap, so order does not matter); `find(source)`
  returns the provider for a record's `vacancy_source`. **An unknown source is not a 500**: `find` returns
  `null` and sync yields `SKIPPED_UNSUPPORTED`.
- **Retries, limits and HTTP client options are a shared framework** (`vacancies/`): backoff, timeout,
  size cap, `validateStatus`. Per-source: env keys (base URL, User-Agent, own timeout/retries), page
  path, error texts. Each source module registers **its own** `HttpModule.registerAsync` — the `baseURL`
  differs, so a shared `HttpService` would send one source's request to another's host.

#### The it-vacancies.ru source

Page path `/vacancies/{id}/` (digits only, trailing slash mandatory in the request — without it the
source answers a redirect, wasting one throttle slot). No public API. Unlike getmatch.ru the
`application/ld+json` `schema.org/JobPosting` block **is** the reliable contract and is present on both
the vacancy page and the results page; `window.__NUXT__` is never evaluated (§2.4) — it is minified
JavaScript, not data. A withdrawn vacancy answers `404` → `NOT_FOUND`; a missing `JobPosting` on a `200`
is fail-loud `ERROR`, exactly like hh.ru. **NOT VERIFIED:** no live page ever showed an "archived"
marker (the flag exists only inside `window.__NUXT__`), so `archived` rests on the project assumption
"withdrawn ⇒ 404", with `IT_VACANCIES_ARCHIVED_MARKER_PATTERN` kept as a documented heuristic. Like
`GETMATCH_USER_AGENT`, `IT_VACANCIES_USER_AGENT` is optional with a safe default (§8).

#### The geekjob.ru source

See §4.13 for the full write-up (page selectors, the internal search JSON endpoint, the salary
grammar, the `sortOrder` publication-date rule). In short: `/vacancy/{24-hex}` HTML page for sync, an
undocumented `/json/find/vacancy` JSON endpoint for search results (the user-facing `/vacancies` page
is client-rendered and empty on raw HTML); a withdrawn/removed vacancy answers `404` → `NOT_FOUND`,
same as it-vacancies.ru; `archived` is always `false` from the vacancy page (NOT VERIFIED as a marker,
only the 404 case is confirmed live) — the search JSON's `log.archived` is the only reliable archived
signal, and it exists only in the paginated results.
