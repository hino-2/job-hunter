### 3.2 Enum `ApplicationStatus`

| Value            | UI label (ru) |
| ---------------- | ------------- |
| `OPEN`           | Открыта       |
| `HR_INTERVIEW`   | HR-собес      |
| `TECH_INTERVIEW` | Тех-собес     |
| `CLOSED`         | Закрыта       |

`OPEN` is the initial value on record creation.

`HR_INTERVIEW` and `TECH_INTERVIEW` are **derived, not user-settable directly**: the backend
computes them on every write (`POST`/`PATCH`) from `hrInterviewAt`/`techInterviewAt` (§3.1) —
see `application-status.helpers.ts` (`deriveInterviewStatus`). Rules, in priority order:

1. `techInterviewAt` non-`null` ⇒ `TECH_INTERVIEW`, regardless of `hrInterviewAt`.
2. Otherwise `hrInterviewAt` non-`null` ⇒ `HR_INTERVIEW`.
3. Otherwise, if the record's status was `HR_INTERVIEW`/`TECH_INTERVIEW` and both dates are now
   `null`, it returns to `OPEN`.
4. None of the above never overrides an effective `CLOSED` — a terminal `result` (§3.3) or an
   explicit `status: CLOSED` sent in the same body always wins over the interview derivation.

**"Active" statuses** (§5.1, §5.2) — `OPEN`, `HR_INTERVIEW`, `TECH_INTERVIEW`, i.e. everything
except `CLOSED` — are the set that `sync-open`, the `status=OPEN` filter and the header counter
operate on; they are grouped as `ACTIVE_APPLICATION_STATUSES`.
