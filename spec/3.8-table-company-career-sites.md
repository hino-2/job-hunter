### 3.8 Table `company_career_sites`

The user-editable list of «Сайты компаний» (§7.9, §5.9) — the rows the `COMPANY_SITE` lead-search
source (§4.14) walks one at a time. Independent of `vacancy_leads` (§3.5): there is no foreign key
between the two tables and never will be. A row is identified only by its own `id`; deleting it does
**not** cascade to, or otherwise touch, leads already found through it — those leads keep existing
with their own `vacancy_url`/`external_id`, exactly as `vacancy_leads` keeps no reference to any
source-specific configuration row of the other three sources either.

| Column (DB)  | DB type         | Req. | Default             | Description                                                             |
| ------------ | --------------- | ---- | -------------------- | ------------------------------------------------------------------------ |
| `id`         | `uuid` PK       | yes  | `gen_random_uuid()`  | Record identifier                                                       |
| `name`       | `varchar(255)`  | yes  | —                     | Company name, shown in the UI and stamped onto every lead found through this row (§4.14) |
| `url`        | `varchar(2048)` | yes  | —                     | The address a parser is picked for (§4.14) — read literally only by the `hh-search` parser, every other parser ignores it beyond dispatch |
| `created_at` | `timestamptz`   | yes  | `now()`               |                                                                          |
| `updated_at` | `timestamptz`   | yes  | `now()`               | Auto-updated on any change                                              |

**Indexes: PK on `id` only.** No uniqueness on `name` or `url` — a duplicate row is the user's own
mistake to avoid, not something the schema enforces; both fields are otherwise free-form.

**Migration:** `CreateCompanyCareerSitesTable1787900000000` creates the table, seeds 11 rows (name,
url — see §4.14 for the parser each one currently resolves to) and inserts the matching
`vacancy_scan_position` row (§3.7) for `source = 'COMPANY_SITE'`, `next_page = 0`.

**Rows are hard-deleted.** `DELETE /api/company-career-sites/:id` (§5.9) removes the row outright —
there is no `hidden`/soft-delete concept here, unlike `vacancy_leads.hidden_at` (§3.5): a company
career site is configuration, not a found vacancy, and re-adding it is one more `POST` away.
