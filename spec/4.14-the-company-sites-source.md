### 4.14 The company-sites source (`COMPANY_SITE`)

The fourth lead-search source (§4.11.0), and the only one that is not a single site: it is a fixed,
user-editable **list** of companies' own career pages (`company_career_sites`, §3.8), each one
resolved to a parser by its host. Module `company-sites/`, dependencies
`company-sites/ → { hh/, vacancies/, applications/ (VACANCY_SOURCE), database/ (COLUMN_TYPE) }`, no
back-reference to `vacancy-search/` — the same one-way rule as the other three source modules.
`COMPANY_SITE` implements only the lead-search contract (§4.8); there is no sync provider and never
will be — a company's own careers page has no single vacancy to poll by ID the way an application
does.

**Page = company index, not a results page.** `CompanySiteSearchService.fetchSearchPage({ page })`
ignores `searchUrlTemplate` (it carries the fixed sentinel `'company-sites'`, see below) and instead
treats `page` as a **0-based row index** into `company_career_sites`, ordered `name ASC, id ASC` — the
same order `GET /api/company-career-sites` (§5.9) uses. `lastPage = count - 1` (or `null` when the
table is empty), so a run walks the list exactly once, company by company, the same loop shape every
other source uses for its results pages.

#### The provider contract: `publicationDateKnown = false`

`VacancyLeadSearchProvider.publicationDateKnown` (§4.8) is `true` for hh.ru, it-vacancies.ru and
geekjob.ru — their results pages report a real publication date — and `false` here: a company's own
careers page virtually never does. Three pipeline rules key off this flag (`vacancy-scan.service.ts`):

1. **No age cut-off.** The `VACANCY_SCAN_MAX_AGE_DAYS` check (§4.11.6) is skipped entirely for a
   `COMPANY_SITE` page — `skippedOld`/`stoppedReason: 'AGE_LIMIT'` never fire for it. `published_at`
   is first-seen (see below), not a real date, so filtering by it would discard vacancies at random.
2. **Deduplication echelon 2 is by `external_id`**, not by the (company, position, date) key (§4.11.5)
   — `VacancyLeadsService.findExistingByExternalIds`, keyed on `(source, external_id)`. The
   four-column key still exists as the table's `UNIQUE` constraint and step-5 insert guard for every
   source including this one, but the echelon-2 lookup that runs **before** the title AI cannot use it
   here: `published_on` is first-seen, so a vacancy seen again a week later would carry a **different**
   `published_on` than its first row and echelon 2 would treat it as new every single day, spending AI
   tokens on it forever.
3. **Stage 0/3.5 always run in `'full'` mode** (`VACANCY_PREFILTER_MODE_WITHOUT_SEARCH_QUERY = 'full'`,
   independent of the global `VACANCY_PREFILTER_MODE` env value) — a company careers page has no
   search query of its own (no `text=…` a user could narrow), so the profile's including keywords
   substitute for it as the cheap deterministic pre-filter; every other source only checks including
   keywords in `'full'` mode when the operator explicitly opts in.

#### The parser registry — dispatch by host, the SSRF boundary

`CompanySiteParserRegistry.resolve(url)` picks the first `CompanySiteParser` whose `matches(url)`
returns `true`; a row whose host matches none of them is skipped (empty page for that company, logged,
counted as neither a failure nor `skippedInvalid` — see below), not an error. **A row's own `url` is
read literally by exactly one parser — `hh-search`.** Every other parser fetches its own fixed,
constant endpoints and ignores the row's `url` beyond the host match itself; this is the whole SSRF
boundary of the module: a user pastes an arbitrary URL into `POST /api/company-career-sites` (§5.9),
but only an `https://` hh.ru host (the existing hh.ru allow-list, §4.2) is ever fetched verbatim.
Every other host is only ever used to *pick* a parser, never dereferenced as given.

#### Lazy pagination — `collectPagedVacancies`

Every parser's `fetchVacancies` walks its own list pages through a shared helper,
`collectPagedVacancies` (`company-sites.helpers.ts`), 0-based, stopping on the first of:
`!hasMore`, a page that added **zero new** `external_id`s (a defence against a source that ignores its
own page parameter and keeps re-serving the same page — observed live on kontur.ru, see below), or
`COMPANY_SITE_MAX_LIST_PAGES = 50` (`ponytail`: a hard ceiling, not adaptive to a source's real depth
— raise it if a source needs more). **One failed list page fails the whole company** — unlike the
other three sources, where one bad results page is skipped and the run moves to the next page
(§4.11.11), here a transport/parse failure on any page of one company's list turns into exactly **one**
`pagesFailed` for that company's "page" of the `COMPANY_SITE` leg, and the run moves on to the next
company row; it does not retry within the company nor abort the whole leg.

#### Identity, dates, logo

- **`external_id = md5(vacancy_url)`**, 32 hex characters (`buildCompanySiteExternalId`,
  `node:crypto`) — there is no source-side ID to reuse the way the other three sources do, and the
  canonical `vacancy_url` each parser builds (constant host + id, or, for `hh-search`, the same
  canonical hh.ru address the `HH` source itself would build) is stable across runs, so the hash is
  stable too.
- **`published_at`/`published_on` is first-seen** (the moment `buildCompanySiteItem` first builds the
  item) for every parser implemented so far, **except** the planned Stage 3 `rzd` parser, which does
  report a real `published_at` from its own API.
- **`logoUrl` is always `null`.** No parser downloads a company logo through the `company-sites/`
  throttle — the `hh-search` parser deliberately drops the logo the underlying `HhSearchService`
  result carries (avoids double-downloading the same hhcdn.ru asset already handled by the `HH`
  source's own lead), and no other parser has found a reliable per-vacancy logo worth the extra
  request.

#### Throttle

One shared `CompanySiteRequestThrottle` (`COMPANY_SITE_MAX_REQUESTS_PER_SECOND`, default `2`) covers
**every** host every non-`hh-search` parser talks to — a single small budget split across dozens of
company domains, not one throttle per domain (§4.11.2 gives every other source its own, because each
one is a single domain). Rows resolved to the `hh-search` parser go through hh.ru's **own**
`HhRequestThrottle`/`HH_MAX_REQUESTS_PER_SECOND` instead — `HhSearchSiteParser` reuses
`HhSearchService` wholesale, throttle included, so a company career page implemented as an hh.ru search
query never competes with the company-sites throttle at all.

**Live verification, `kontur` (2026-09-27, `curl -A "Mozilla/5.0 job-hunter/1.0"`):**
`https://kontur.ru/career/vacancies?page=1` redirects (`301`) to the same URL with no query string;
`?page=2` answers `200` **byte-identical** to `?page=1` — the whole vacancy list (50 items, grouped
into rubrics) is rendered on one server response regardless of `page`, and further pages (if any) are
loaded client-side through `/ajax/career/vacancies/list`, which this project's plain-`GET`-only parser
(§12 — no headless browser) never calls. `collectPagedVacancies`'s "zero new ids" stop rule already
handles this without special-casing the source: page 2 repeats page 1's ids verbatim, so the walk ends
after one wasted extra request, not by looping to `COMPANY_SITE_MAX_LIST_PAGES`. Anchor markup:
`<a class="vacancy" href="/career/vacancies/{id}">` with the title in its own child
`<span class="vacancy__title">…</span>`, followed by a `<div class="vacancy__description">` holding
city/work-format text — the title is read from that child span directly, not by collapsing the
surrounding whitespace/`&nbsp;` runs. The vacancy's own page carries a `<main class="page-layout__content">`
block; `extractPageText` yielded 11581 characters of plain-text body from a live sample, comfortably
over the 200-character floor (`COMPANY_SITE_MIN_DESCRIPTION_CHARS`).

**Live verification, `x5` (2026-09-27):** `https://x5.tech/vacancy?page=1`/`?page=2` are **real**,
non-overlapping pages of 10 items each (Next.js). Anchor markup:
`<a title="…" class="VacanciesItem_title__…" href="/vacancy/{uuid}">…</a>` — the CSS-module class
carries a build-specific hash suffix and is deliberately **not** part of the match pattern (only
`href`'s UUID shape is); the anchor's inner HTML is already the plain title text, no nested tags. The
vacancy's own page has both `<main>` and `<body>`; `extractPageText` yielded 4568 characters from a
live sample.

#### Known limitations

- **Same-title collapse.** Two different URLs, from the same company, carrying the exact same title
  on the same calendar day collapse into one row — both the in-run `Set` (echelon 1, §4.11.5) and the
  `UNIQUE` index key on (source, company, position, date) key on the title text, and `published_on`
  here is first-seen (today, for both), not a real distinguishing date. Accepted: this project has no
  per-source uniqueness weaker than the shared four-column key, and adding one just for `COMPANY_SITE`
  would be a special case for a rare collision.
- **`hasApplication` for a `COMPANY_SITE` lead is computed by exact `vacancy_url` match, not by
  (`vacancy_source`, `vacancy_external_id`).** `ApplicationsService.resolveVacancyRef` (§4.2) never
  recognizes a company career site's own host (only hh.ru/getmatch.ru/it-vacancies.ru/geekjob.ru are
  in `VacancyProviderRegistry`), so an application created from such a lead is saved with
  `vacancySource: null` — the (source, externalId) pair the other three sources match on would never
  match again, and a second click on «Отклик» would silently create a duplicate application.
  `VacancyLeadApplicationService` therefore branches on the lead's `source`: for `'COMPANY_SITE'` it
  looks the existing application up by `vacancy_url` equality instead (`ApplicationsService.findOneByVacancyUrl`/
  `findAppliedVacancyUrls`) — safe because every `COMPANY_SITE` parser builds `vacancy_url`
  canonically and identically on every run (constant host + id, or, for `hh-search`, the same
  canonical address the `HH` source itself builds), so the stored value and the lead's value are the
  same string. See §5.7 for the resulting `hasApplication` contract.
- **Resume is by row index** (§4.11.12) — adding or deleting a `company_career_sites` row shifts every
  index after it, so «Продолжить» after editing the list may skip or repeat a company. Accepted: the
  list changes rarely, and a `FRESH` run is one click away.
- **Ozon's own careers site is out of scope** (anti-bot protection, §12) — the seeded Ozon row instead
  targets an hh.ru search query (`hh-search` parser) scoped to that employer, which is within the
  project's existing hh.ru allow-list and throttle. Any company whose own careers page only links out
  to hh.ru vacancies, rather than hosting them, is covered the same way — an `hh-search` row, not a
  dedicated parser.
