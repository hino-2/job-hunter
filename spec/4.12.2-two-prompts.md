#### 4.12.2 Two prompts

Two prompts in settings (§3.6, §7.9): `title_prompt` (stage 1, the **title**) and `description_prompt`
(stage 4, the **description**). Placeholders expanded before sending:

| Placeholder     | Allowed in           | Replaced with                                          |
| --------------- | -------------------- | ------------------------------------------------------ |
| `{keywords}`    | both prompts         | The `keywords` list from settings, comma-separated     |
| `{titles}`      | `title_prompt` only  | Numbered list of the batch's titles                    |
| `{title}`       | `description_prompt` | Current vacancy title                                  |
| `{company}`     | both prompts         | Company name                                           |
| `{description}` | `description_prompt` | Description, converted to text and truncated (§4.11.7) |

Validation on saving settings (§5.7): `title_prompt` must contain `{keywords}` and `{titles}`,
`description_prompt` must contain `{keywords}` and `{description}`; otherwise `400` with a clear message.
Default prompts (created by a migration, editable on the frontend):

```
title_prompt:
Ты помогаешь отбирать вакансии для разработчика. Ключевые слова профиля: {keywords}.
Подходит только тот, кто сам пишет код продукта: разработчик, программист, developer, engineer.
Отклоняй любые другие специальности, даже если в названии есть слово fullstack:
тестировщика и QA, аналитика (системного, бизнес, любого), менеджера, дизайнера,
devops, преподавателя, руководителя без разработки.
Разработчик подходит и тогда, когда его основной язык другой, но в названии есть
React, Node.js, TypeScript или JavaScript.
Разработчик подходит, если название не уточняет стек вовсе.
Названия:
{titles}
Ответь JSON-массивом по одному объекту на каждое название, в том же порядке.
```

```
description_prompt:
Ты помогаешь отбирать вакансии. Данные размечены блоками.
<keywords>{keywords}</keywords>
<title>{title}</title>
<company>{company}</company>
<description>{description}</description>
Блок <keywords> — это профиль кандидата, а НЕ текст вакансии: слова оттуда нельзя
приписывать вакансии и нельзя цитировать как её требования.
Реши, требует ли вакансия технологии профиля как основные, а не упоминает их вскользь.
Если основной стек вакансии не пересекается с профилем, ответ — false.
Ответь JSON-объектом с полями:
matches — true или false;
reason — обоснование на русском, опирающееся ТОЛЬКО на блоки <description> и <title>;
evidence — дословная цитата из блока <description>, подтверждающая ответ, скопированная
посимвольно и без слов из других блоков.
```

The `<keywords>`/`<title>`/`<company>`/`<description>` block markers are mandatory in the default text —
a small model (`qwen3:4b-instruct`) otherwise conflates the plain keyword list on line 1 with the vacancy
title and cites it back as evidence for a match that does not exist (§4.12.3). Placeholder names are
unchanged. The old text stays in migration `CreateVacancySearchSettingsTable` as a snapshot;
`SharpenVacancyTitlePrompt` rewrites `title_prompt`, `BlockDelimitVacancyDescriptionPrompt` rewrites
`description_prompt` to the block-delimited text above — both only where the user has not edited the
prompt by hand.

Known limitation: the block markers are a formatting aid for a small model, **not** a trust boundary.
`htmlToPlainText` (`backend/src/common/html.helpers.ts:34-37`) strips tags before unescaping HTML entities,
so a source page whose description contains an escaped `&lt;/description&gt;` yields a literal
`</description>` in the model input and could close the block early. This is not fixed here: the real
guards against a fabricated verdict are the evidence grounding check and the deterministic stop-word
filter (§4.12.3, §4.11.4), neither of which a forged delimiter defeats, and adding delimiter escaping or
sanitizing would be speculative abstraction against a threat those two mechanisms already cover (§12).
