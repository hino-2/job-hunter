#### 4.12.3 Response format and reliability

The response is requested **structured**: in Ollama the `format` field with a JSON Schema in
`POST /api/chat`; for OpenAI-compatible providers `response_format`. Stage 1 schema — an array of
`{ index: number, matches: boolean, reason: string }` of exactly the batch size; stage 4 — an object
`{ matches: boolean, reason: string, evidence: string }`. `reason` is truncated to the column width (500)
before writing; `evidence` is a verification input only and is **never stored** — it never leaves the
stack frame of `VacancyAiService.judgeDescription` except as a log fragment on failure. Other parameters:
`temperature: 0`, `VACANCY_AI_TIMEOUT_MS` (default 30 000), no retries on timeout. The default assumes a
GPU (measured on an RTX 5070); on the CPU-only setup that §4.12.4 also supports, a cold model load plus a
full stage-1 batch can exceed 30 s even with output now bounded, so a CPU-only operator should raise
`VACANCY_AI_TIMEOUT_MS` — a growing `aiFallbacks` counter with no other errors in the log is the symptom
that it is currently too low.

**Output caps.** The JSON Schema itself bounds `reason` and `evidence`, with a narrower `reason` bound
on stage 1 than on stage 4: stage 1 `reason` (`maxLength: 100`, `VACANCY_AI_TITLE_REASON_MAX_LENGTH`)
justifies only a coarse title-level cut and is shared by up to `VACANCY_AI_BATCH_SIZE_MAX` (30) verdicts
under one generation cap, so it is bounded tighter than stage 4's `reason` (`maxLength: 200`,
`VACANCY_AI_REASON_MAX_LENGTH`); stage 4's `evidence` (`maxLength: 300`) is the verbatim quote checked
below. The grammar of structured output (GBNF in Ollama, structured outputs in OpenAI) makes the model
close the string early, actually shortening generation, which clamping an already received string
cannot do. `vacancy-lead.builder.ts` still clamps to the column width (500) as the last line of defence
for any provider/model with a longer `reason`. Independently, every request also carries a hard cap on
the number of generated tokens — `num_predict` for Ollama, `max_tokens` for OpenAI-compatible providers
(`AiChatRequest.maxOutputTokens`). This cap is a **ceiling, not a reservation**: tokens the model does
not generate cost nothing, so a generous ceiling is free in the normal case, and its only job is to stop
a runaway generation — so each ceiling is set comfortably *above* the point where its own schema
saturates, not tight against it.

These ceilings, and `VACANCY_AI_BATCH_SIZE_MAX` itself, are **measured**, not estimated: on a live
Ollama running `qwen3:4b-instruct` (a different model has its own tokenizer, and every number below
shifts with it), a realistic stage-4 verdict (`reason` at 200 Cyrillic chars, `evidence` at 300 Cyrillic
chars, plus JSON structure) costs 163–182 tokens across several realistic samples, confirmed end-to-end
with a description crafted to force the model to quote up to the `maxLength` cutoff (175 tokens
generated). `VACANCY_AI_DESCRIPTION_MAX_OUTPUT_TOKENS` (280) leaves ≈ 54% margin over the measured
maximum. Stage 1 uses
`VACANCY_AI_TITLE_OUTPUT_TOKENS_OVERHEAD + VACANCY_AI_TITLE_OUTPUT_TOKENS_PER_ITEM * batchSize`
(16 + 72 per item), scaling with batch size; a realistic `reason` at exactly the 100-char cap costs
28–39 tokens plus 13 tokens of per-item JSON structure (worst measured verdict ≈ 52 tokens), so `PER_ITEM
= 72` leaves ≈ 38% margin — the same order as stage 4's, not the near-zero margin an earlier, unmeasured
estimate implied. `OVERHEAD = 16` covers the `{"verdicts":[…]}` wrapper (6 measured tokens) with room for
Ollama's indented, non-compact JSON formatting. The real title prompt (`title_prompt` from
`vacancy_search_settings` plus the rendered titles block) measures ≈ 415 fixed tokens + ≈ 20 tokens per
title. At `VACANCY_AI_BATCH_SIZE_MAX = 30` the prompt (≈ 1015) plus the stage-1 output ceiling (≈ 2176)
together use ≈ 78% of `n_ctx = 4096`, leaving the required ≥ 15% headroom; a raw batch of 50 would put the
output ceiling alone (16 + 72 × 50 = 3616) at 88% of `n_ctx` before the prompt is even counted, which is
why the ceiling — not throughput — is what caps the batch size (§4.12.4: `VACANCY_AI_BATCH_SIZE_MAX` is
about the protocol, not performance — above it llama.cpp silently truncates/shifts an overflowed context
instead of erroring, and the only visible symptom is a verdict-count mismatch, not a clear failure).
A generation truncated by this cap yields unparsable or incomplete JSON, which is deliberately
the *same* failure class as an invalid response below — no separate handling path exists for it.
OpenAI structured outputs with `strict: true` reject `maxLength` and other unsupported validation
keywords in the schema with a `400`; the OpenAI adapter therefore strips them
(`stripUnsupportedSchemaKeywords`, `openai-schema.helpers.ts`) before sending, so the shared schema
stays single-sourced and the protocol quirk lives in the adapter's own module.

**Grounding check (stage 4 only).** `evidence` must be a substring of the description actually sent to
the model (the same text, already clamped to `VACANCY_AI_DESCRIPTION_MAX_CHARS`) after both sides are run
through the same normalization: case-insensitive, whitespace collapsed to one space, typographic quotes/
dashes/ellipsis folded to plain ASCII, `ё` → `е`. Purely a normalized-substring check — no fuzzy or
similarity matching. The schema's `evidence` `maxLength` only makes the model close the quote earlier
than intended — a `maxLength`-truncated `evidence` is still a **prefix** of the verbatim quote and
therefore still a normalized substring of the description, so the check itself is unaffected. A
normalized `evidence` shorter than 3 characters never grounds (kills degenerate
quotes like `""`, `"."`, `"-"` that would trivially substring-match anything). The check runs only when
`matches === true` — a negative verdict stores nothing, so a fabricated quote there costs nothing, and
requiring grounding on a reject would turn a correct rejection into a fallback that could then create the
lead. This exists because a small model (`qwen3:4b-instruct`) has been observed citing the profile's
`{keywords}` list back as if it were text from the vacancy's own description (§4.12.2).

**Any AI failure is not a run failure.** Timeout, unavailable container, invalid JSON, array length not
matching the batch, or (stage 4 only) an ungrounded `evidence` → that batch/vacancy is decided by keywords
(§4.11.4), `match_source = 'KEYWORDS'`, counter `aiFallbacks`, `warn` in the log. An ungrounded quote is
deliberately the *same* failure class as invalid JSON rather than a `rejectedDescription`: it means there
is no verdict to rely on, not that the model looked and said no, and with the §4.11.4 stage 3.5 stop-word
check in place ahead of it, the keyword fallback for this case is safe. Fallback-selected vacancies do not
go through stage 4. The model that issued the verdict is written to `ai_model`.
