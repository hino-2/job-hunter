#### 4.11.5 Deduplication

The key is **source + normalized company + normalized position + publication date** (`source`,
`company_key`, `position_key`, `published_on`), materialized by a unique index (§3.5). Normalization
uses the §4.11.4 function plus a clamp to column width. Normalized values must be stored as **separate
columns**, not an index expression (a functional index would need an `IMMUTABLE` DB function). Three
echelons:

1. **Within a run** — a `Set` of processed keys, applied **right after exclude keywords, before AI**: one
   results page easily holds regional clones with identical title, company and date. A clone counts into
   `duplicates`, not `rejectedTitle`. The `Set` is shared by every leg of a multi-source run (§4.11.0), but
   this is safe precisely because the key carries the source: an hh.ru key and a geekjob.ru key for the same
   title/company/date are different strings by construction, so an earlier leg can never swallow a later
   leg's copy of the same vacancy.
2. **Against the DB, before the title AI** (§4.11.4 stage 1) — one `SELECT` over every survivor of stage 0
   and echelon 1 (`WHERE source = … AND (company_key, position_key, published_on) IN (…)`), source as an
   equality predicate rather than a fourth element of the `IN` tuples, because one page of results belongs to
   exactly one leg; a hit updates `last_seen_at` and counts into `duplicates`, never reaching the model.
   Running this **before** rather than after the title AI is the point: at the default 40-page depth most
   candidates on a re-run are already known, and judging their title again would be a wasted AI call. As a
   consequence `last_seen_at` is now refreshed for every known lead on the page, not only for those that
   would have passed the title model.
3. **On insert** — `INSERT … ON CONFLICT DO NOTHING`; the unique index stays the source of truth.

A duplicate is not silent: the existing row's `last_seen_at` is updated and it counts into `duplicates`.
**A hidden vacancy is still a duplicate** — `hidden_at` must not affect deduplication, otherwise hidden
entries would return every run. The date is part of the key on purpose: without it a re-publication of the
same vacancy a month later would be collapsed.

**Cross-posting is deliberately NOT deduplicated.** The same vacancy published on both hh.ru and
geekjob.ru is **two leads**, and both must reach the selection — hiding a copy on one board must not hide
the copy on another, and the user may want to apply through either. The cost is paid knowingly: each copy
spends its own title/description AI pass and its own slot of the shared `VACANCY_SCAN_MAX_DETAILS` budget
(§4.11.8).
