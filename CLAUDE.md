# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Источник истины

**[SPECIFICATION.md](./SPECIFICATION.md) — источник истины проекта.** Читай релевантный
параграф перед любой правкой: код и комментарии в нём ссылаются на разделы (`§4.3`, `§5.5`, …).
Ключевые разделы: §2.4 зафиксированные тех. решения, §3 модель данных, §4 интеграция с hh.ru,
§5 REST API, §10 код-конвенции, §12 вне скоупа, §14 порядок разработки с отметками о готовности.

Порядок разработки (§14) идёт шагами; шаги 1–14 сделаны, включая финальный проход (шаг 11).
Дальнейшая работа — точечные правки поверх готового приложения, и каждая обязана оставить
в §14 отметку о сделанном. §12 перечисляет то, что делать **нельзя** (cron, пагинация, тёмная
тема, JWT, экспорт и т. д.) — не добавляй это по своей инициативе.

## Пайплайн разработки (обязателен)

**ВСЕГДА** веди разработку через цепочку агентов, без исключений и «мелких правок мимо»:

1. **`architect`** — первым шагом на любую новую фичу, шаг §14, рефакторинг или нетривиальное
   изменение. Читает релевантные параграфы SPECIFICATION.md и текущий код, выдаёт блюпринт:
   состав файлов, типы, потоки данных, границы модулей. Код не пишет.
2. **`backend-developer` / `frontend-developer`** — реализуют строго по блюпринту. Бэкенд-код
   не отдавать фронтенд-агенту и наоборот.
3. **`code-reviewer`** — сразу после каждой реализации. Ищет реальные баги, нарушения §10
   и расхождения с блюпринтом; код не меняет, отдаёт отчёт.
4. Найденные ревьювером проблемы чинит тот же developer-агент; после правок — повторное ревью,
   пока отчёт не станет чистым.

Только после чистого ревью — `npm run lint`/`typecheck`/`test`/`build` и коммит шага.

## Команды

Всё запускается из корня; воркспейсы — `backend` и `frontend`.

```bash
npm run lint            # eslint в обоих воркспейсах (lint:fix — с автоправкой)
npm run typecheck       # tsc --noEmit в обоих
npm run test            # jest (backend, unit) + vitest (frontend)
npm run build           # сборка обоих
npm run format          # prettier --write

npm run dev:api         # backend в watch-режиме, http://127.0.0.1:3000/api
npm run dev:web         # vite, http://127.0.0.1:5173 (проксирует /api на 3000)

npm run up / down / logs / ps   # docker compose
```

Один тест:

```bash
npm run test --workspace=backend -- hh-url.parser        # по имени файла
npm run test --workspace=backend -- -t "имя теста"       # по названию
npm run test --workspace=frontend -- src/App.test.tsx
```

e2e бэкенда (нужен поднятый Postgres — тесты идут против настоящей БД):

```bash
docker compose up -d db
npm run test:e2e --workspace=backend
npm run test:e2e --workspace=backend -- applications     # один e2e-файл
```

Миграции (`synchronize` выключен навсегда, схема — только миграциями):

```bash
npm run migration:generate --workspace=backend -- src/database/migrations/ИмяМиграции
npm run migration:run --workspace=backend
npm run migration:revert --workspace=backend
```

В Docker миграции накатываются автоматически перед стартом `api`.

## Архитектура

```
браузер → web (nginx :8080) → api (NestJS :3000) → db (PostgreSQL :5432)
                                     ↓
                            публичный API hh.ru
```

Наружу опубликован только `web`, и только на `127.0.0.1`. Фронт всегда ходит на относительный
`/api`: в дев-режиме проксирует Vite, в Docker — nginx.

**Монорепо на npm workspaces** без turbo/nx: один `package-lock.json` в корне, общий тулинг
(TypeScript, ESLint, Prettier) — в корневых `devDependencies`, чтобы версии не разъезжались.

### Backend (NestJS + TypeORM)

- **`app.setup.ts` (`configureApp`) — единственное место настройки приложения**: префикс `/api`,
  глобальный `ValidationPipe`, `BasicAuthGuard`, `HttpExceptionFilter`. Его зовут и `main.ts`,
  и e2e-фабрика (`test/e2e-app.factory.ts`), поэтому тесты гоняют ровно прод-поведение.
  Guard и filter регистрируются вручную через `useGlobalGuards`/`useGlobalFilters`, а **не** через
  `APP_GUARD`/`APP_FILTER` — иначе появилось бы второе место настройки. Добавляешь глобальное
  поведение — добавляй туда.
- **Basic Auth глобальный** (`auth/basic-auth.guard.ts`): закрыт весь `/api/*`, кроме помеченного
  `@Public()` (`GET /api/health`). Сравнение — `timingSafeEqual` по SHA-256-дайджестам; в лог
  не попадают ни заголовок Authorization, ни логин, ни пароль.
- **Формат ошибок единый** (`common/http-exception.filter.ts`, §5.5): `{ statusCode, message, error }`,
  стек — только в лог. `@Catch()` без аргументов ловит всё, включая `QueryFailedError`.
  Ответ отправляется через `response.status().json()`, чтобы не затереть `WWW-Authenticate`.
- **Валидация env при старте** (`config/environment.validation.ts`): отсутствующая или невалидная
  переменная роняет процесс. Новая env-переменная = поле в `EnvironmentVariables` + дефолт-константа
  в `config/config.constants.ts` + строка в `.env.example` + проброс в `docker-compose.yml`.
- **Слои**: контроллер маппит сущность в DTO (`ApplicationDto.fromEntity`) и переводит доменные
  исходы в HTTP-статусы; сервис возвращает сущности и говорит на языке `SyncOutcome` (§4.5),
  потому что его переиспользует и синхронизация, и preview.
- **`hh-url.parser.ts` — чистая функция, а не провайдер**: её зовёт и `ApplicationsService`,
  и `HhController`, зависимостей у неё нет, а провайдер обязывал бы каждого вызывающего тянуть
  за собой модуль. Enum `SyncOutcome` объявлен в `applications/applications.constants.ts`,
  потому что зависимость идёт `hh → applications` (колонка `last_sync_outcome` — в `applications`).
- **`hh-api.service.ts` исключений наружу не бросает**: любой сбой (429, 5xx, таймаут, битый JSON)
  превращается в исход `SyncOutcome`. Ретраи — только на 429 и 5xx. Значения, попадающие в БД
  (`type.id` → `hh_vacancy_type`), режутся по ширине колонки прямо в `toHhVacancy`: иначе слишком
  длинное значение от hh.ru дало бы 500 вместо штатного исхода.
- **`hh_vacancy_id` вычисляется на бэкенде** при создании и при **каждой** записи `vacancy_url`
  (включая очистку в `null`); фронт это поле не присылает.
- **Порядок маршрутов**: `POST 'sync-open'` и `POST ':id/sync'` объявлены **выше** методов
  с `:id`, иначе Express сматчит `sync-open` как `:id`. Не переставлять.
- **`vacancies/vacancy-sync.service.ts` — единственное место правил §4.3**: собирает
  `ApplicationSyncPatch` (в нём нет и не может быть `company`/`result`; `position` пишется
  только при исходе `OK` и только непустым нормализованным заголовком источника —
  `vacancy-position.helpers.ts` режет его по ширине колонки, иначе длинный заголовок дал бы
  500 вместо штатного исхода) и сам сохраняет запись через
  `Repository<Application>`. Зависимость модулей идёт `ApplicationsModule → VacanciesModule → { HhModule, GetmatchModule }`,
  обратного импорта нет — иначе цикл и `forwardRef`. Эндпоинты §5.2 отвечают `200` на любой
  исход; `404` — только «нет записи в БД». Патч применяется к сущности до `save()`, поэтому
  на упавшем `save()` сущность откатывается по снимку (`ApplicationSyncSnapshot`) — в ответ
  не должно уехать состояние, которого в БД нет.
- **`vacancy_source`/`vacancy_external_id` пишутся только парой и только на пути записи
  `vacancy_url`** (`ApplicationsService.resolveVacancyRef`); `VacancySyncService.decide()`
  доверяет колонке и URL не разбирает. Data-миграция, трогающая любую из этих двух колонок,
  обязана менять их вместе, а её `down()` — откатывать собственный backfill:
  `GeneralizeVacancySource` этого не делал, и цикл revert→up склеил getmatch-шный id
  с источником `'HH'` (починено миграцией `RepairGetmatchVacancySource`).
- **Массовый прогон** (`common/async.helpers.ts`, `mapWithConcurrency`): слот времени
  резервируется синхронно, до `await`, иначе все воркеры стартуют одновременно. Хелпер ошибки
  не глушит и прогон не отменяет — их ловит `syncOneSafely`, чтобы одна запись не срывала
  остальные (§4.6); подробности сбоя уходят в лог, наружу — обобщённый текст, как в §5.5.
- Сущность (`application.entity.ts`) — эталон для `migration:generate`; маппинг snake_case ↔ camelCase
  задаётся явным `name` в каждой колонке, кастомной NamingStrategy нет.

### Frontend (React + MUI + Vite)

Провайдеры — в `main.tsx` (ThemeProvider + LocalizationProvider ru с `localeText` пикеров +
QueryClientProvider). Единственный HTTP-клиент — `api/client.ts`; заголовков авторизации фронт
не хранит, Basic Auth подставляет сам браузер.

- **`App.tsx` — единственный владелец локального состояния**: фильтры, раскрытость аккордеонов,
  несохранённые правки и уведомление. Серверные данные живут только в React Query, глобального
  стора и React-контекста нет (§2.2). Контекст здесь именно вреден: он пробивает `memo`
  на аккордеоне, и каждое нажатие клавиши перерисовывало бы весь список. Поэтому колбэки собраны
  в один стабильный объект (`InlineEditHandlers`), а меняющиеся данные идут в аккордеон **срезами
  по id** (`pendingById[id]`, `savedById[id]`) — только так `memo` спасает соседей.
- **Раскрытость аккордеонов едет в список данными, а не колбэком** (`hooks/useExpandedIds.ts`):
  хук отдаёт `expandedIds: ReadonlySet<string>` и отдельный объект `actions`, идентичность
  которого постоянна на всё время жизни экрана. Предикат `isExpanded`, замкнутый на состояние,
  менял идентичность контроллера на каждое переключение, а через него — и `handleToggle`,
  и проп `onToggle` у **каждого** аккордеона: один клик перерисовывал весь список. `actions`
  уходит в зависимости `handleToggle`, поэтому мутаторы обязаны оставаться с пустыми deps;
  «всё ли раскрыто» считает чистая `utils/expanded-ids.utils.ts` — внутри хука она сделала бы
  `expandAll` зависимым от `ids`. В аккордеон уходит `boolean`-срез `expandedIds.has(id)`.
- **`ApplicationFields` и `ApplicationSummaryRow` под `memo`, детали монтируются лениво**
  (`mountOnEnter: true` при выключенном `unmountOnExit`, §7.2). Причина — не микрооптимизация:
  `TextareaAutosize` под многострочными полями объявляет layout-эффект `syncHeight` без массива
  зависимостей и меряет себя после каждого рендера, форсируя синхронный пересчёт layout всего
  документа, а свёрнутый `Collapse` прячет содержимое `visibility: hidden`, а не `display: none`
  — то есть измеряются и свёрнутые записи. Проп-литерал (объект или лямбда прямо в JSX)
  в этих двух компонентах молча вернёт задержку: `memo` работает ровно потому, что
  `mergeApplicationWithPending` при пустом черновике возвращает **ту же ссылку**,
  а `savedFields`/`handlers` стабильны.
- **`hooks/useInlineEdits.ts` — черновики и подсветка «сохранено» для всего списка** (§7.3).
  Правило: **черновик живёт ровно от нажатия клавиши до отправки.** В момент отправки он
  снимается, и поле показывает оптимистичное значение из кэша — тот же текст, мигания нет, зато
  «догоняющий» ответ сервера не может затереть набранное. Исключения ровно два: черновик
  не снимается, когда в патч уходит тримленное значение (иначе пауза после пробела съедала бы
  этот пробел и уводила каретку), и черновик недонабранной ссылки не снимается никогда.
  Состояние держится здесь, а не в компоненте полей, из-за §13.10.7: свернуть аккордеон можно
  и кликом по шапке, и кнопкой «Свернуть все», оба пути идут через `App`, поэтому pending-правку
  удаётся отправить **до** сворачивания. Черновик в компоненте потребовал бы `useEffect`
  на смену пропа `expanded`, что запрещает `react-hooks/set-state-in-effect`. Источник истины
  по черновикам — ref, состояние лишь его зеркало для рендера: `flush` — обработчик события
  и обязан читать актуальные черновики, а звать `mutate` внутри функционального апдейтера
  `setState` нельзя (в StrictMode он выполняется дважды).
- **`ApplicationAccordion` мержит черновик в запись один раз** и отдаёт результат и в шапку,
  и в поля — отсюда §13.10.8 «правка сразу видна в свёрнутой шапке» без единой дополнительной
  строки. Компонент обёрнут в `memo`.
- **`hooks/useUpdateApplication.ts` — автосейв одного поля**: оптимистичный патч кэша и
  **пополевой** откат при ошибке. Контекст мутации — снимок ровно отправленных полей, а не всей
  записи: откат снимком вернул бы к устаревшему соседнее поле, сохранённое параллельно, пока
  этот запрос летел. Инвалидация — только на смену `status` (она меняет состав отфильтрованного
  списка и счётчик §7.8); после правки остальных полей перезагрузка вредна, ответ заменил бы
  массив целиком и мигнул бы значением поля, которое правят прямо сейчас. Snackbar и подсветку
  хук не рисует — зовёт `onSaved`/`onFailed`, уже приведя кэш в порядок. Колбэки живут
  на хуке, а не на вызове `mutate`: второй `mutate` отцепляет предыдущую мутацию
  от `MutationObserver`, и call-site-колбэки первой не сработали бы.
- **`hooks/useSyncApplication.ts` — синхронизация одной записи (§7.6)**, и набор
  синхронизирующихся id живёт **в самом хуке**: `isPending`/`variables` у `useMutation` описывают
  только последний `mutate`, а кликнуть 🔄 на двух строках подряд можно — вторая кнопка «отвисла»
  бы вместе с первой. Набор меняется функциональным `setState` в `onMutate`/`onSettled`, поэтому
  парность держится на всех путях; в аккордеон уходит **срез-`boolean`**, иначе набор целиком
  пробил бы `memo` у всех соседей на каждый старт и финиш. Из ответа переносятся только колонки
  синхронизации (`buildSyncEchoPatch`) — замена записи целиком откатила бы оптимистичное значение
  поля, которое правят прямо сейчас. В число этих колонок входит и `position` (§4.3 в новой
  редакции), но переносится она только при `outcome === 'OK'` и только непустая: при прочих
  исходах бэкенд должность не писал, поэтому хелпер и принимает `SyncResult` целиком. `404` вычищает запись из кэшей (удалена в другой вкладке).
- **`hooks/useSyncAllOpen.ts` — массовый прогон (§7.7)**: `applications[]` из ответа в кэш
  сознательно **не** вливается — только инвалидация префикса, потому что членство записи
  в отфильтрованных выборках и её позиция в чужих сортировках клиенту неизвестны. Инвалидация
  идёт и в `onError`: прогон синхронный и мог отработать в БД, а ответ — не доехать по таймауту.
  Таймауты `/sync` и `/sync-open` подняты пер-запросно: дефолтные 20 с короче штатного худшего
  случая одной записи на бэкенде (≈32 с) и оборвали бы успешный запрос.
- **Сводка прогона — отдельный `SyncSummaryAlert` в потоке страницы, а не `useNotification`**:
  тому нужно одно короткое автогасящееся сообщение, а сводке — раскрывающийся список проблемных
  записей, живущий до явного закрытия. Три канала исходов не смешиваются: неуспешный `outcome`
  при HTTP 200 → Snackbar с severity по §7.6; сбой запроса → error-Snackbar;
  `ERROR`/`RATE_LIMITED` внутри успешного ответа → только `Alert` сводки.
- **Отключённая 🔄 обёрнута в `span` со `stopPropagation`**: MUI ставит отключённому `IconButton`
  `pointer-events: none`, и клик по спиннеру проваливался бы в шапку аккордеона (§13.10.3).
- **`utils/applications-cache.utils.ts` — единственное место, знающее форму кэша.** Обе функции
  работают префиксным фильтром по `APPLICATIONS_QUERY_KEY`: он накрывает разом все закэшированные
  комбинации фильтров и ключ счётчика шапки. Патч возвращает **ту же ссылку** на массив, если
  записи в нём нет, иначе React Query пометит изменёнными все кэши подряд.
- Заведомо невалидные значения (пустая обязательная «Компания», кривой URL) на сервер
  не отправляются вовсе — вместо гарантированного 400 поле показывает `error` и `helperText`.
  Клиентская проверка URL при этом **мягче** серверного `@IsUrl`, а не строже: иначе валидная
  ссылка стала бы несохраняемой.
- Enum-ы статуса/результата и лимиты длин дублируются вручную в `constants/`-файлах фронта
  (общий shared-пакет заводить не нужно, §3.4). Значения зазоров, flex-basis, порогов и таймингов
  берутся из `constants/layout.constants.ts` и `constants/query.constants.ts`, в JSX числовых
  литералов размеров нет (§13.10.6).

### e2e-инфраструктура

`test/test-environment.ts` (`applyTestEnvironment`) вызывается **до** импорта `AppModule` и
подменяет `process.env`: отдельная БД `jobhunter_test` (пересоздаётся с нуля каждый прогон,
имя проверяется регексом и на несовпадение с рабочей базой), фиксированные креды Basic Auth
и `HH_API_BASE_URL` на локальную заглушку (`test/hh-stub.server.ts`). **Ни один e2e не ходит
в интернет** — новые тесты синхронизации обязаны использовать эту же заглушку. Изоляция между
тестами — `TRUNCATE`, поэтому `maxWorkers: 1`.

## Обязательные конвенции (§10)

1. **Константы уровня модуля — только в `*.constants.ts`** соответствующего модуля. Инлайн-объявление
   в имплементационном файле запрещено (включая контроллеры, модули, конфиги, компоненты, vite.config).
2. **Типы — в `*.type.ts`, интерфейсы — в `*.interfaces.ts`** того же модуля. Единственное исключение:
   в spec-файле допустим инлайновый тип мока, используемого только внутри этого spec.
3. **Пустая строка** после блока объявлений переменных и после каждой закрывающей скобки блока.
   Правило `@stylistic/padding-line-between-statements` (`eslint.shared.mjs`) поймает нарушение —
   Prettier пустые строки не расставляет.
4. **Никаких `any`.** Внешние данные приходят как `unknown` и сужаются явными предикатами
   (см. `toHhVacancy`, `buildErrorResponse`).
5. **Коммиты без trailer `Co-Authored-By: Claude…`** и без упоминаний процесса, лимитов и перерывов —
   только суть изменения. Комментарии, сообщения об ошибках и логи — на русском, как в остальном коде;
   комментарий объясняет _почему_, а не _что_.

## Зафиксированные решения — не пересматривать (§2.4)

- **TypeScript ровно 5.9.3**, не 7.x: `typescript-eslint` требует `<6.1.0`, `ts-jest` — `<7`.
- **Нет `@nestjs/cli`**: сборка — `tsc -p tsconfig.build.json`, дев — `node --watch --require ts-node/register`.
  esbuild/swc/tsx использовать **нельзя** — они не поддерживают `emitDecoratorMetadata`, без которой
  ломается DI в Nest и маппинг в TypeORM.
- **`consistent-type-imports` выключен на бэкенде** по той же причине: класс, используемый только как
  тип параметра конструктора, обязан импортироваться как значение. На фронте правило включено.
- **`database/data-source.ts` экспортирует ровно один `DataSource`** (только `export default`) —
  иначе TypeORM CLI падает.
- **`@stylistic/padding-line-between-statements`**, а не ядровое правило ESLint (deprecated, удаляется в ESLint 11).
